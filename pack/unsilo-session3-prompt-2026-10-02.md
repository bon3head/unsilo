### Layer 1 — Relational data theory (pack/unsilo-data-theory-2026-10-02.md)

One SQLite file, two schemas. `staging` holds raw, tentative, partial data
(the Duolingo-format ingest lands here). `core` holds promoted, verified,
auditable data. Promotion staging to core is an explicit, receipted
transition, never silent. Partial data lives in staging with provenance;
v1 hardens the promotion rules, not the tables.

Entity inventory (core): company (one row per real company, never per name
variant); name_variant (company_id, variant, source) where entity
resolution lives, never merged in a string column; filing (company_id,
filing_type, accession/id, filed_at, artifact_hash); claim (atomic unit:
one checkable assertion, source quote, artifact ref); verdict (claim_id,
status in {confirmed, killed, downgraded, unresolved}, decided_at,
decided_by, rationale) as ROWS so claims carry verdict history; blocker
(title, status, falsifier, owner, opened_at, closed_at); application
(company_id, role, platform, req_id, status, applied_at, terms);
action_item; audit_run + audit_finding; artifact (sha256, path,
captured_at), content-addressed, a claim that cannot join to it is
UNRESOLVED by construction; expectation (entity_id,
expected_artifact_type, expected_window, status in {fulfilled, missing,
late, refuted}): absence-as-signal made relational, ordered by expected
probability descending with status=missing first.

Normalization: core is 3NF/BCNF. The feed read path is a denormalized VIEW
(feed_item), never a table.

Temporal modeling (the B4 layer): bitemporal valid_time vs
transaction_time. Interval endpoints are explicit markers, never overloaded
NULL: a timestamp, UNBOUNDED_FUTURE, or UNKNOWN. NULL means "not recorded"
and nothing else. Open intervals stay open; every query handles the open
case explicitly.

Receipts: append-only ledger; every core mutation writes before/after hash
receipts BEFORE landing. Repair replays the ledger; history is never
edited. feed_item orders by (event_time, id); no LIMIT without ORDER BY.

Indexing/search: indexes on (event_time DESC), (company_id, event_time),
status columns. FTS5 over claim text and feed bodies, rebuilt on
promotion. WAL mode, single writer, foreign keys enforced. Migrations:
numbered, forward-only, hash-receipted; core changes only by migration.
